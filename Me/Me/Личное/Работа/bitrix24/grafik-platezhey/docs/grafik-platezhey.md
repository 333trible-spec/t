# ТЗ — «График платежей» (MVP)

> Черновик. Своё приложение вместо маркетплейсного (ITISO), чтобы не зависеть от чужого
> сервера и хранить данные у себя. Статус: согласуем объём и открытые вопросы.

## 1. Зачем

По сделке нужно завести **план платежей** (когда, сколько, какими частями клиент платит).
На выходе — не кастомный смарт-процесс, а **стандартные счёта Битрикса**: под каждый платёж
графика создаётся счёт с нужной суммой и сроком оплаты, привязанный к сделке. Дальше оплату
и просрочку ведём **штатным** функционалом счетов.

## 2. Границы MVP

**Делаем:**
- вкладка-калькулятор графика в карточке сделки;
- генерация N стандартных счетов из графика (все сразу).

**Пока НЕ делаем (вернёмся позже):**
- напоминания о платежах в чат;
- автосмена стадии сделки при просрочке;
- автосоздание задач при платеже;
- сводный дашборд по всем сделкам — под вопросом.

## 3. Модель графика (главная идея)

Внутри — **одна таблица платежей**, всегда редактируемая. Строка = `№ | дата оплаты | сумма`.
«Тип графика» — это лишь способ **заполнить** таблицу:

| Тип | Что задаёт пользователь | Как заполняет таблицу |
|---|---|---|
| **Равными частями** | полная сумма, кол-во платежей, аванс (первый платёж), дата первого платежа, частота | аванс — **первая строка** (часть полной суммы), остаток `(сумма − аванс)` раскидывает равными долями по датам |
| **Полная оплата** | полная сумма, дата | одна строка на всю сумму |
| **Индивидуальный** | строки вручную | пустая таблица, добавляешь сам |

**Полная сумма** подтягивается **из суммы сделки** (`opportunity` сделки), не вводится руками.
**Частота** для «равными частями»: `ежемесячно`, `раз в квартал`, `произвольный интервал
(каждые N месяцев)`.

**Правки:** любую строку можно поправить руками. При изменении суммы строки — остаток
**пересчитывается на оставшиеся** строки, чтобы `Σ строк = полная сумма`.

**Проверки перед созданием:** сумма всех строк равна полной сумме; даты идут по возрастанию;
нет нулевых/отрицательных сумм.

## 4. Создание счетов

Кнопка **«Создать счета»** → для каждой строки графика один счёт через `crm.item.add`
(`entityTypeId = 31`). Все счета создаются сразу.

Поля счёта (проверено на портале dm-tmn):

| Поле счёта | Код | Что кладём |
|---|---|---|
| Сумма | `opportunity` | сумма строки графика |
| Срок оплаты | `closedate` | дата платежа из строки |
| Дата выставления | `begindate` | сегодня (дата создания графика) |
| Стадия | `stageId` | `DT31_2:N` (Новый) |
| Сделка | `parentId2` | id текущей сделки |
| Компания | `companyId` | из сделки |
| Ответственный | `assignedById` | из сделки |
| Название | `title` | напр. «Платёж 3/14 — {название сделки}» |
| Валюта | `currencyId` | RUB |

Воронка счетов — одна, **«Общая»** (`categoryId = 2`).

## 5. Отметка оплаты и просрочка — штатно

- «Оплачено» = перевод счёта на стадию **«Оплачен»** (`DT31_2:P`) — руками, в Битриксе.
- «Дата оплаты» = `movedTime` (дата, когда счёт уехал в «Оплачен»).
- Список платежей по сделке, фильтр просрочки — **встроенные** списки счетов. В MVP свою
  вкладку «Платежи» и отчёт по просрочке **не делаем** — их роль играет Битрикс.

Стадии воронки счетов (для справки): `N` Новый · `S` Отправлен клиенту · `P` Оплачен ·
`D` Не оплачен. Нам важны только **Новый** и **Оплачен**.

## 6. Пересоздание графика (правки после создания счетов)

График **можно переделать** и после того, как счета уже созданы. При повторном сохранении
идёт **сверка** новых строк графика с ранее созданными счетами (не «удалить всё и создать
заново», а аккуратная синхронизация):

- **Оплаченные счета** (`DT31_2:P`) — **неприкосновенны**: не меняем и не удаляем.
- **Неоплаченные счета** — можно **редактировать** (сумма/срок) под новые строки.
- Если строк стало **меньше** — лишние неоплаченные счета **удаляем**.
- Если строк стало **больше** — недостающие **создаём**.

Приоритет — **редактирование и удаление лишних**, а не полное пересоздание (чтобы не плодить
номера счетов).

**Следствие про пересчёт:** оплаченные суммы фиксированы; при пересчёте «равными» остаток
`(полная сумма − уже оплачено)` распределяется только по **неоплаченным** строкам.

> Для этого график и связку «строка графика ↔ id счёта» надо **хранить у себя** — см. п. 7.

## 7. Хранение графика

Храним, потому что без этого не сделать сверку из п. 6. Новая таблица в `timereport.db`
(напр. `payment_schedules` + `payment_schedule_items`): `deal_id`, параметры графика, строки
и **id созданного счёта** по каждой строке, дата создания/обновления.

## 8. Решённые вопросы

- **Аванс** — часть полной суммы (первая строка), не сверху. ✅
- **Пересоздание** — сверка со счетами, оплаченные не трогаем (п. 6). ✅
- **Хранение графика** — да, у себя (п. 7). ✅
- **Частота** — ежемесячно / раз в квартал / произвольный интервал (N месяцев). ✅
- **Полная сумма** — из суммы сделки, без ручного ввода. ✅
- **Валюта/НДС** — на старте только рубли, без разбивки НДС. ✅
- **Ответственный** за счёт — из сделки. ✅
- **Дата выставления** — сегодня (дата создания графика). ✅

Объём MVP согласован. Ниже — как реализуем.

## 10. Как реализуем (архитектура)

Ложится в существующий проект `timereport/` по той же схеме, что вкладки «Дашборд»/«Проект»:
Flask-роут отдаёт статичную HTML-страницу с внедрённым `DEAL_ID`, страница ходит в наши
`/api/...`, а те дёргают Битрикс через **вебхук** (как `fetcher.py`).

### 10.1 Встройка (placement)
- Отдельное VibeCode-приложение «График платежей», placement **`CRM_DEAL_DETAIL_TAB`**,
  `appUrl → {APP_URL}/schedule`. (Как «Дашборд»; заголовок вкладки фиксируется при создании.)
- Ставится рядом с существующими вкладками, на тип договора **не завязано** (график можно
  вести по любой сделке).

### 10.2 Роуты (в `app.py`)
- `GET /schedule` — отдаёт `static/schedule.html`, внедряет `window.DEAL_ID` (как `/tab`).
- `GET /api/schedule?deal=ID` — вернуть текущее состояние:
  - параметры и строки сохранённого графика (если есть);
  - сумму сделки, компанию, ответственного, название (из `crm.deal.get`);
  - актуальные стадии созданных счетов → флаг `paid` по каждой строке.
- `POST /api/schedule/apply` — принять `{deal, type, params, rows[]}`, провести **сверку**
  со счетами (см. 10.4), сохранить снимок. Мутирующий → под `_is_admin()`, с подтверждением
  в UI («будет создано/изменено N счетов»).

### 10.3 Новый модуль `payments.py`
Вся логика по счетам и графику (чтобы `app.py` оставался тонким), рядом с `project.py`:
- `deal_context(deal_id)` — сумма/компания/ответственный/название сделки;
- `build_equal(total, advance, count, first_date, freq)` — сгенерировать строки
  (аванс = первая строка, остаток равными долями, копейки округляем — «хвост» на последнюю
  неоплаченную строку, чтобы `Σ = total`);
- `add_months(d, n)` — сдвиг даты (месяц=1, квартал=3, N) с корректным концом месяца;
- `list_deal_invoices(deal_id)` — `crm.item.list` (`entityTypeId=31`, `parentId2=deal`),
  вернуть id, сумму, срок, стадию;
- `apply_schedule(deal_id, rows)` — сверка и запись (см. 10.4).

Вызовы Битрикса — те же помощники, что в `fetcher.py` (`_get`, `_post_batch`):
`crm.deal.get`, `crm.item.add / update / delete / list` c `entityTypeId=31`.

> ⚠️ **Только свои счета.** На сделке могут быть **чужие** счета (заведённые вручную или
> другими приложениями — напр. на сделке 850 уже висит 8 таких). Наш модуль управляет
> **исключительно теми счетами, которые создал сам**: по сохранённым у нас `invoice_id`, плюс
> помечаем свои счёта `xmlId = paysched:{deal}:{seq}` для надёжной пере-идентификации. Чужие
> счета **никогда** не редактируем и не удаляем. Списком `parentId2=deal` пользуемся только для
> справки/показа, но не как источником «что чистить».

### 10.4 Алгоритм сверки (`apply_schedule`)
1. Загрузить сохранённый график и id ранее созданных счетов (**только наши**, см. предупреждение выше).
2. Спросить у Битрикса актуальные стадии этих счетов → множество **оплаченных** (`DT31_2:P`).
3. Провалидировать вход: `Σ строк = сумма сделки`; даты по возрастанию; суммы > 0;
   **оплаченные строки не изменены** (иначе отказ).
4. Сверка:
   - **оплаченные** счета — оставить как есть;
   - **неоплаченные** существующие счета сопоставить по порядку с неоплаченными новыми строками:
     - на пересечении — `crm.item.update` (сумма/срок);
     - лишние существующие — `crm.item.delete`;
     - недостающие строки — `crm.item.add` (стадия `DT31_2:N`, поля из п. 4 ТЗ).
5. Сохранить новый снимок графика со свежими `invoice_id` по строкам.

### 10.5 Хранение (в `db.py`)
```sql
CREATE TABLE payment_schedules (
    deal_id     INTEGER PRIMARY KEY,
    kind        TEXT,      -- 'equal' | 'full' | 'custom'
    total       REAL,      -- зафиксированная сумма на момент создания
    advance     REAL,
    count       INTEGER,
    freq_months INTEGER,   -- 1 | 3 | N
    first_date  TEXT,      -- 'YYYY-MM-DD'
    created_at  TEXT,
    updated_at  TEXT
);
CREATE TABLE payment_schedule_items (
    deal_id    INTEGER,
    seq        INTEGER,    -- порядковый номер строки
    due_date   TEXT,       -- срок оплаты
    amount     REAL,
    invoice_id INTEGER,    -- id созданного счёта (NULL, пока не создан)
    PRIMARY KEY (deal_id, seq)
);
```

### 10.6 Фронт (`static/schedule.html`)
- Читает `window.DEAL_ID`, грузит `GET /api/schedule`.
- Показывает сумму сделки (только чтение), выбор типа, параметры (кол-во/аванс/первая дата/
  частота) и **редактируемую таблицу** строк.
- «Заполнить» — считает строки на клиенте; правка строки пересчитывает остаток по неоплаченным.
- Оплаченные строки — помечены и заблокированы.
- «Сохранить и создать счета» → `POST /api/schedule/apply`, затем показать результат
  (создано/изменено/удалено) и ссылки на счета.

### 10.7 Порядок работ
1. `db.py` — таблицы + функции чтения/записи графика.
2. `payments.py` — генерация строк, `add_months`, вызовы Битрикса, сверка.
3. `app.py` — роуты `/schedule`, `/api/schedule`, `/api/schedule/apply`.
4. `static/schedule.html` — форма + таблица.
5. Регистрация placement-приложения в Битриксе (отдельная вкладка).
6. Проверка на «живой» сделке, деплой через `deploy.py`.
