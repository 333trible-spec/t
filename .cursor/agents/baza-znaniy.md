## Инциденты — отдельный документ на каждый

**Обязательное правило:** каждый **инцидент** оформляется как **отдельный документ** (отдельная статья) в базе знаний Битрикс24.

- Один исходный файл с несколькими инцидентами → **разбить** на несколько статей: **1 инцидент = 1 документ БЗ**.
- Несколько файлов об одном инциденте → **одна** статья с объединением фактов; в отчёте перечислить все исходные файлы.
- Не объединять разные инциденты в одну статью, даже если они в одном файле или одной теме.
- Название статьи — **как в исходнике**: «Инцидент N» или смысловой заголовок («Недоступен реквизит»). Не переименовывать без запроса.
- **Без** блока «Краткое описание».
- **Без** блока «Связанные материалы» (в образце инцидентов нет).
- Блок Wellsoft в конце файла Б24 — **внутрь инцидента 6**, не отдельная статья.

Если границы инцидента в исходнике неочевидны — не публиковать; пометить **«Требует проверки»** и описать, как предлагаешь разбить.

## Алгоритм для каждого документа

1. Получить файл / экспорт из Google Drive.
2. Определить: название, тему, логическую структуру, ключевые разделы, таблицы, списки, инструкции, ссылки, изображения.
3. Преобразовать в markdown для БЗ 2.0 **строго по образцу** (не `##` заголовки):

```markdown
**Формулировки клиентов:** [варианты через / в одной строке]

**Описание сценария для повторения ошибки:** [текст]

**Теги**: `тег1`, `тег2`

**Причина:** [текст]

**Решение**: (*роли*) [алгоритм]
**Решение 2**: (*роли*) …  — если в исходнике несколько решений
```

   - формулировки — через `/`, не списком `-`;
   - теги — в `` `backticks` ``;
   - первое решение — **Решение**, далее **Решение 2**, **Решение 3**;
   - роли в скобках курсивом: `(*Клиент, Интегратор, ПМ*)`;
   - маркированные списки внутри решения — допустимы, если были в исходнике;
   - **без** «Краткого описания» и «Связанные материалы».
4. Сохранить смысл без искажений; не придумывать факты.
5. Убрать дубли, мусорное форматирование, лишние переносы, неинформативные фразы.
6. Устаревшее / противоречивое / неполное — **не исправлять**, пометить: **«Требует проверки»**.
7. Слишком большой документ **без выделенных инцидентов** — разбить на связанные статьи по смысловым блокам. Если в документе **инциденты** — применять правило **1 инцидент = 1 документ БЗ** (см. выше), а не общее разбиение по объёму.
8. Несколько документов одной темы (не инциденты) — предложить структуру разделов и подразделов.
9. Названия статей — **как в исходнике** (см. правило инцидентов выше).

## Публикация через REST (БЗ 2.0)

- API: `/rest/api/.../note.document.*` (не `/rest/` — будет 404).
- Создание: `note.document.add` с `collectionId: 16`, `parentId` из таблицы папок, `markdown`.
- Обновление: `note.document.update` с `overwrite: true`.
- `position` через API **не меняется** — порядок в папке см. skill.

### Скрипты (`kb-migration/scripts/`)

| Скрипт | Назначение |
|--------|------------|
| `parse-b24.js` / `parse-1c.js` | Парсинг export → markdown |
| `publish-b24-rest.js` | Публикация инцидентов Б24 (нумерованные) |
| `publish-1c.js` | Публикация инцидентов 1С (смысловые заголовки) |
| `fix-incident-order.js` | Порядок «Инцидент 1, 2, 3…» (parent 74) |

Черновики: `kb-migration/drafts/` и `drafts/1C/`.

## Порядок в папке

Дерево БЗ сортирует соседние страницы по `position` **по убыванию**. Для порядка как в исходнике:
- нумерованные инциденты Б24 — создавать **7 → 1**, затем `fix-incident-order.js`;
- смысловые заголовки (1С) — `publish-1c.js` (пересоздаёт первые N−1 для выравнивания).
